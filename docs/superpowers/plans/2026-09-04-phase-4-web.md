# Фазы 4 и 5: веб-слой и интерфейс

**Цель.** Загрузил книгу в браузере, посмотрел текст, нажал озвучить,
получил m4b. Состояние живёт на сервере, закрытая вкладка ничего не ломает.

**Архитектура.** Один процесс FastAPI. Пользователь один, задача одна,
поэтому ни брокера, ни отдельного воркера. Синтез в фоновом потоке,
состояние в SQLite в режиме WAL.

## Ключевые решения

**Почему не Celery и не Redis.** Замеры фазы 1: книга на 15 часов считается
20 минут. Одна задача за раз, один пользователь. Очередь на SQLite
и `ThreadPoolExecutor(max_workers=1)` покрывают это целиком.

**Почему SSE, а не WebSocket.** Поток строго в одну сторону: сервер шлёт
прогресс. Отмена делается обычным POST.

**Почему предпросмотр обязателен.** Синтез книги это 20 минут машинного
времени. Увидеть мусор до, а не после, дешевле в 20 минут.

## Задачи

### 4.1: Хранилище задач
`book2audio/web/jobs.py`. SQLite в WAL, таблица jobs: id, состояние, путь
к файлу, параметры, прогресс, ошибка, время. Состояния: `uploaded`,
`extracting`, `ready_for_review`, `synthesizing`, `done`, `failed`,
`cancelled`. Переходы проверяются: из `done` в `synthesizing` нельзя.

### 4.2: Фоновый исполнитель
`book2audio/web/runner.py`. Один поток, очередь на таблице. Прогресс
пишется в БД, оттуда его читает SSE. Отмена через флаг, проверяемый
между чанками.

### 4.3: HTTP-слой
`book2audio/web/main.py`. Загрузка файла, разбор, предпросмотр, запуск,
прогресс через SSE, скачивание, отмена, удаление.

### 4.4: Интерфейс
`book2audio/web/static/`. Одна страница, ванильный JS, без сборщика.
Четыре экрана: загрузка, предпросмотр, прогресс, готово.
Оформление по elman-practices:elman-design.

## Критерий готовности

```bash
uv run book2audio serve
```

Загрузка книги, правка текста, синтез с живым прогрессом, скачивание m4b.
Закрытие вкладки на середине синтеза не убивает задачу.
